# Mixed-frequency State Feature v1

Status: ready-for-agent

## Problem Statement

FineFT currently has target-frequency bar features, Base_Time_feature, Cross-Month Term Structure Feature, Rolling Window Feature, Risk State Feature, and Liquidity State Feature. These features describe the current bar, recent target-frequency windows, contract lifecycle, and cross-month structure, but they do not provide a compact low-frequency market context for each intraday bar.

The user wants to add Mixed-frequency State Feature support so each target-frequency bar can observe prior completed daily and weekly market state without leaking current-day, current-week, or future information into training.

## Solution

Add a first version of Mixed-frequency State Feature generation for commodity futures. The v1 scope is intentionally narrow:

- Mixed-frequency Base Data is materialized first: daily base data has one row per TradingDay, and weekly base data has one row per calendar week.
- Daily base data and weekly base data are generated by separate code entrypoints before Mixed-frequency State Feature generation.
- Daily Mixed-frequency State Feature and weekly Mixed-frequency State Feature are generated by separate code entrypoints before the combined Mixed-frequency State Feature artifact is written.
- Daily mixed-frequency features use only the previous complete TradingDay.
- Weekly mixed-frequency features use only the previous complete calendar week, where calendar week membership is derived from TradingDay.
- Daily sliding-window and weekly sliding-window features are out of scope for v1.
- Current-day and current-week period-to-date features are out of scope for v1.

The generated features should be joined onto target-frequency bars as candidate State Feature columns, following the same broad pattern as existing Base_Time_feature and Cross-Month Term Structure Feature integration. Reward/Execution columns must not receive these features.

## User Stories

1. As a futures research user, I want each intraday bar to include previous-day market context, so that the RL agent can observe low-frequency state without inferring it from short target-frequency windows.
2. As a futures research user, I want each intraday bar to include previous-calendar-week market context, so that the RL agent can distinguish slow weekly regimes from intraday noise.
3. As a futures research user, I want daily features to use only the previous complete TradingDay, so that current-day final statistics never leak into earlier bars.
4. As a futures research user, I want weekly features to use only the previous complete natural week, so that current-week final statistics never leak into earlier bars.
5. As a futures research user, I want week membership to be based on TradingDay, so that night session Event Timestamp behavior does not corrupt the weekly boundary.
6. As a futures research user, I want the first version to exclude daily sliding-window features, so that the initial implementation is easy to validate.
7. As a futures research user, I want the first version to exclude weekly sliding-window features, so that the initial weekly join rule is unambiguous.
8. As a futures research user, I want previous-day return and range features, so that the model can observe the prior completed day direction and volatility.
9. As a futures research user, I want previous-day candlestick shape features, so that the model can observe whether the previous TradingDay closed strong or weak.
10. As a futures research user, I want previous-day VWAP/TWAP deviation and trade-direction ratio features, so that the model can observe recent market activity without absolute levels.
11. As a futures research user, I want previous-day OpenInterest change features, so that the model can observe position-building or position-reduction pressure.
12. As a futures research user, I want previous-day turnover-rate style features, so that volume can be interpreted relative to OpenInterest.
13. As a futures research user, I want previous-week return and range features, so that the model can observe slow directional and volatility context.
14. As a futures research user, I want previous-week VWAP/TWAP deviation and trade-direction ratio features, so that the model can observe weekly participation without absolute levels.
15. As a futures research user, I want previous-week OpenInterest change features, so that the model can observe weekly positioning changes.
16. As a futures research user, I want missing previous-period features to be handled deterministically, so that early sample rows do not silently create NaN State Feature values.
17. As a futures research user, I want invalid input columns to fail fast, so that malformed source data does not silently contaminate training.
18. As a futures research user, I want mixed-frequency columns to remain separate from Reward/Execution columns, so that they participate in Feature Selection and Scale Save like candidate State Feature columns.
19. As a futures research user, I want feature names to identify previous-day versus previous-week origin clearly, so that Feature Selection Manifest and Scale Manifest remain interpretable.
20. As a futures research user, I want tests around Monday and mid-week bars, so that the calendar-week causality rule is proven rather than assumed.

## Implementation Decisions

- Add a Mixed-frequency State Feature generator for commodity futures.
- Add separate Daily Base Feature and Weekly Base Feature generators for commodity futures.
- The daily base generator should materialize daily OHLCV data with one row per TradingDay.
- The weekly base generator should materialize weekly OHLCV data with one row per calendar week.
- The daily feature generator should consume daily Mixed-frequency Base Data plus target-frequency bar timestamps to map each bar to a previous TradingDay.
- The weekly feature generator should consume weekly Mixed-frequency Base Data plus target-frequency bar timestamps to map each bar to a previous calendar week.
- The combined feature writer should merge the daily and weekly Mixed-frequency State Feature files by timestamp.
- v1 daily features:
  - `prev_day_return`
  - `prev_day_range_pct`
  - `prev_day_body_pct`
  - `prev_day_upper_shadow_pct`
  - `prev_day_lower_shadow_pct`
  - `prev_day_close_position`
  - `prev_day_body_to_range`
  - `prev_day_upper_shadow_to_range`
  - `prev_day_lower_shadow_to_range`
  - `prev_day_vwap_deviation_pct`
  - `prev_day_twap_deviation_pct`
  - `prev_day_trade_up_ratio`
  - `prev_day_trade_down_ratio`
  - `prev_day_trade_imbalance`
  - `prev_day_open_interest_change`
  - `prev_day_turnover_rate`
- v1 weekly features:
  - `prev_week_return`
  - `prev_week_range_pct`
  - `prev_week_body_pct`
  - `prev_week_close_position`
  - `prev_week_body_to_range`
  - `prev_week_upper_shadow_to_range`
  - `prev_week_lower_shadow_to_range`
  - `prev_week_vwap_deviation_pct`
  - `prev_week_twap_deviation_pct`
  - `prev_week_trade_up_ratio`
  - `prev_week_trade_down_ratio`
  - `prev_week_trade_imbalance`
  - `prev_week_open_interest_change`
  - `prev_week_turnover_rate`
- Daily aggregation is based on TradingDay, not Event Timestamp calendar date.
- Weekly aggregation is based on the natural calendar week containing each TradingDay.
- For a target-frequency bar in TradingDay `D`, daily features must come from the immediately previous available TradingDay before `D`.
- For a target-frequency bar in calendar week `W`, weekly features must come from the immediately previous complete calendar week before `W`.
- Do not implement daily or weekly sliding-window features in v1.
- Do not implement period-to-date current day or period-to-date current week features in v1.
- Feature values should be finite before they are emitted. Division by zero or unavailable previous-period denominators should produce a deterministic finite fallback, preferably `0.0`, consistent with nearby feature behavior.
- The daily feature output and weekly feature output may be implemented behind one high-level mixed-frequency interface, so downstream merge code has one optional mixed-frequency input.
- Mixed-frequency features should be joined into the future/state candidate feature frame, not the reward feature frame.
- The merge behavior should follow existing optional feature joins used for Base_Time_feature and Cross-Month Term Structure Feature.
- The feature generator should preserve the project glossary terms: TradingDay, Event Timestamp, State Feature, Feature Selection, Scale Save, and Mixed-frequency Visibility Rule.

## Testing Decisions

- Test external behavior at the highest practical seam: given small target-frequency bar inputs spanning multiple TradingDays and natural weeks, the mixed-frequency feature output should show the correct previous-day and previous-week values on each bar.
- Test the merge seam: when mixed-frequency features are supplied to daily feature assembly, the columns appear in the future/state candidate feature frame and do not appear in the Reward/Execution frame.
- Reuse prior art from tests that verify Base_Time_feature and Cross-Month Term Structure Feature joins.
- Reuse prior art from tests that verify fail-fast validation and finite feature output for risk/liquidity features.
- Include a Monday scenario: bars in a new natural week must use the prior natural week, not the partially completed current week.
- Include a mid-week scenario: bars on Tuesday through Friday must still use the same prior natural week, not current-week aggregation.
- Include a first-day or first-week scenario: when no previous complete period exists, output must be deterministic and finite according to the chosen fallback rule.
- Include an OpenInterest denominator scenario: non-positive previous OpenInterest must not produce NaN or infinite values.
- Tests should assert feature behavior and visibility rules, not private helper implementation details.

## Out of Scope

- Daily sliding-window mixed-frequency features.
- Weekly sliding-window mixed-frequency features.
- Current-day period-to-date features.
- Current-week period-to-date features.
- Macro, inventory, fundamental, or external data features.
- Cross-contract or Cross-Month Term Structure Feature changes beyond joining the new mixed-frequency columns beside existing candidate State Feature columns.
- Feature Selection algorithm changes.
- Scale Save algorithm changes.
- RL model architecture changes.

## Further Notes

The glossary has been updated to define Mixed-frequency State Feature, Calendar-week State Feature, Previous-period State Feature, and Mixed-frequency Visibility Rule. The v1 design intentionally starts with only previous complete daily and weekly periods to reduce leakage risk and make the first implementation easy to audit.

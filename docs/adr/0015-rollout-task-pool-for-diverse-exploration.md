# 多样化训练探索任务池与解耦 Worker 架构

为了在低层强化学习多样化训练中充分利用多核算力（如 96~128 核）并消除切片时长差异带来的木桶屏障，我们将探索子进程从绑定单个行情切片的模式重构为解耦的探索 Worker 任务池。

## 决策背景与上下文

在原设计中，每个探索子进程绑定到固定且非重叠的行情数据切片（`df_index`），且在每个 `(context_index, initial_action)` 任务派发后设置全局同步等待屏障。由于实际数据集通常仅划分为约 16 个切片文件，并发度被硬性封顶在 16 个进程以内；同时不同切片数据长度差异显著（相差达 7 倍），快进程在每个动作阶段均需长时间空转等待最慢切片。

## 决策内容

1. **解耦探索 Worker**：每个探索 Worker 启动时预加载全量训练切片数据（16 个切片总计 34MB），具备执行任意切片、任意子代理与任意初始动作模拟的能力。
2. **共享任务池 (Diverse Rollout Task Pool)**：在 Epoch 探索开始时，主进程将全部 $N \times |A_{\text{pos}}| \times |DF|$ 个探索任务推入共享任务队列，所有 Worker 进程竞争拉取任务并流式回传结果，消除动作间的一切同步屏障。
3. **单核限制与参数暴露**：Worker 子进程显式设置 `torch.set_num_threads(1)` 避免多进程前向推理的 CPU 线程争抢；新增 CLI 参数 `--diverse_num_workers`（默认 96），移除硬编码上限。
4. **原子任务协议 (Atomic ExploreTask)**：以单一原子消息 `ExploreTask` 发送任务，Worker 内部自闭环完成环境初始化并探索至 Done，彻底消除多消息跨进程状态错位风险。
5. **模型参数零冗余同步**：策略网络权重在 Epoch 启动时通过配置一次性下发至各 Worker，任务队列中的消息为轻量元组，避免向队列重复写入数百份张量参数。
6. **流式收集与标量聚合**：主进程流式接收各 Worker 回传的轨迹并直接写入体制分层经验池，整轮收齐后统一聚合写入 Context 维度的 TensorBoard 标量。

## 影响与后果

- **计算性能**：CPU 利用率实现线性扩展，在 96 核配置下整轮探索耗时预计降低 70%~85%，彻底解决切片长短不均的木桶效应。
- **内存占用**：96 个进程加载全量切片仅占用约 3.3GB 内存，对 62GB 宿主环境极度安全。
- **作用边界**：本次重构仅作用于多样化训练探索阶段（`parallel_diverse_train.py`），预训练 Warmup 逻辑保持原有实现以控制变动风险。
